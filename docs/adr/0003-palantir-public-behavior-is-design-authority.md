# ADR-0003: Palantir public behavior is the product design authority

- **Status:** Accepted
- **Date:** 2026-08-13
- **Scope:** product purpose, Ontology, OSDK, Functions, Actions, Builder, MCP applications, generated vertical Agent OS products, and future public-behavior work
- **Related:** [Functions/ObjectSet parity matrix](../functions-object-set-parity-matrix.json), [AI FDE parity matrix](../ai-fde-parity-matrix.json), [Action Types parity matrix](../action-types-parity-matrix.json), [Pipeline Builder parity matrix](../pipeline-builder-parity-matrix.json)

## Context

Foundry-lite can only remain a coherent general-purpose platform if each vertical Agent OS uses the
same Ontology-centered operating model instead of inventing a new SaaS architecture for every
domain. The intended loop is data and evidence → typed operational objects → governed functions
and decisions → authorized actions → durable outcomes. That product purpose is visible throughout
Palantir's official Foundry documentation.

Without a hard source rule, a feature can look similar in a demo while violating the deeper
contract: eager arrays can masquerade as ObjectSets, raw REST can masquerade as an OSDK, generated
screens can bypass typed resources, and code existence can masquerade as an operational workflow.

## Decision

### 1. Public product purpose and behavior are authoritative

Every significant product ADR must state the relevant official Palantir pages. Product names,
states, typed resource boundaries, permission intersections, lazy/eager behavior, interaction
semantics, and completion meaning follow that public behavior unless an explicit Foundry-lite
extension is recorded.

### 2. Private implementation identity is not claimed

“Same” means the same publicly documented purpose and observable contract. It does not mean copied
source code, private service topology, proprietary deployment internals, trademarks, screenshots,
or pixel-for-pixel UI. When the public documentation does not reveal an internal choice,
Foundry-lite chooses the smallest architecture that preserves the public invariant and records it
as an implementation choice.

### 3. Every capability carries five linked records

A capability cannot become `current` unless it has all five:

1. an exact official Palantir source;
2. a plain-language public behavior statement;
3. Foundry-lite implementation paths;
4. executable proof tests or operator evidence;
5. explicit remaining gaps, with zero gaps required for that bounded `current` row.

The machine-readable parity matrices are the registry for these links. A broad “full parity” claim
is forbidden while any relevant row remains `partial`, `foundation`, `planned`, or `missing`.

### 4. The Ontology and generated OSDK are mandatory boundaries

Domain agents and their ChatGPT MCP UI operate on typed Objects, ObjectSets, Functions, and Actions.
Generated applications use their app-owned high-level OSDK rather than hand-building generic REST
requests. Runtime reads and writes preserve tenant, application, user, role, scope, masking,
idempotency, optimistic concurrency, audit, and approval boundaries.

### 5. Natural-language generation changes metadata, not platform architecture

A restaurant, accounting, tax, lending, hospital, property, manufacturing, or quant workflow is
generated by changing domain records, states, policies, Functions, Actions, evidence, roles, and
screen copy. It does not create a separate backend architecture. Domain-specific financial, legal,
medical, or tax correctness still requires authoritative data and responsible expert signoff.

### 6. Foundry-lite extensions remain visibly labelled

ChatGPT-native MCP widgets, portable deployment bundles, or other Foundry-lite-specific experiences
may extend the public contract. They must be identified as extensions, must not replace a missing
native behavior in a parity claim, and must preserve the same typed Ontology and governance
invariants.

### 7. Official-source drift is reviewed, not silently absorbed

Each matrix records a verification date. When official documentation changes, the affected rows are
re-reviewed before their status is raised. A removed, inaccessible, or contradictory source lowers
the claim until executable evidence and the matrix are reconciled.

## Consequences

- Product discussions begin with the operational Ontology loop, not a collection of endpoints or a
  generic SaaS page builder.
- Generated Agent OS products must expose Functions and ObjectSets through their generated OSDK.
- New major ADRs and every `*parity-matrix.json` file fail CI if they lack official Palantir sources.
- Current, partial, and future boundaries remain visible to non-developers.
- The platform can add verticals without forking its core architecture.

## Non-goals

- Reverse engineering or copying Palantir private systems.
- Claiming legal, financial, medical, tax, or trading correctness from platform structure alone.
- Treating official documentation as proof that Foundry-lite code works; executable local/live
  evidence remains mandatory.
- Claiming pixel, brand, commercial packaging, hosting, or operational-scale identity.
