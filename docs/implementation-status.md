## Current Reality

- Storage adapter: local SQLite database plus filesystem object storage by default; optional MinIO/S3-compatible object storage is available through `S3DatasetStorageAdapter` and the `s3-storage` adapter profile. The second infra ratchet adds `IcebergDatasetStorageAdapter` and the `iceberg` profile: each dataset version is one Iceberg table snapshot (pinned by `snapshot_id`) with data/metadata in object storage and a SQL catalog tracking the pointer, covered by `quality:iceberg` against MinIO/Testcontainers. Iceberg now keeps Foundry sidecar manifests beside the table data so commit-time branch/created_at and real object-byte hashes are recoverable on read; duplicate-version guard catalog timeouts fail closed as retryable adapter failures. Dataset preview reads use the storage-port `preview_file_paths(...)` boundary, so Iceberg preview validates the pinned snapshot file list and downloads verified manifest data files directly instead of materializing the whole snapshot through `to_arrow()` for ordinary bounded previews. Iceberg multi-part commits now preserve multiple data files inside the pinned snapshot, and `data_file_paths(..., partition_filter=...)` can use manifest column stats/sort bounds to download only matching files without full snapshot materialization. The third infra ratchet adds `SparkComputeAdapter` and the `spark` compute profile (selected independently of storage via `FOUNDRY_LITE_COMPUTE_PROFILE`): Spark runs CSV ingest and SQL transforms on local parquet that the engine materializes from any storage profile, output commits through the dataset transaction protocol, same-session concurrent transforms use per-run temp views, and Spark row-batch CSV staging preserves quoted JSON/CDC strings, covered by `quality:spark`. The composition ratchet is now explicit: `quality:infra-composition` boots `adapter_profile=iceberg` with `FOUNDRY_LITE_COMPUTE_PROFILE=spark` against a MinIO warehouse so Spark reads Iceberg-on-S3 pinned inputs and commits output back to Iceberg-on-S3, including a failure→abort proof. The same composition gate now covers Debezium CDC on the active stack: Debezium-normalized events archive into an Iceberg-on-S3 changelog through Spark, replay into CDC object indexing, skip a stale post-delete update, materialize `ops.order_current`, and prove archive writer failure leaves no raw CDC dataset version. `quality:distributed-control-plane` now groups the PostgreSQL metadata control-plane plus MinIO/S3 + Iceberg + Spark failure-abort proof, live Kafka broker archive worker proof, PostgreSQL-backed parallel Kafka worker cursor-CAS duplicate-commit proof, Temporal product workflow proof, workflow ledger CAS, dataset commit CAS, and Record DLQ replay lease fencing. Genuinely distributed Spark executor/cluster failure modes still need a real cluster and are deferred. CI now acts as an automated reviewer: proof-matrix, source-of-truth, and operator-evidence contract gates read the single `docs/infra-tricky-matrix.json` and emit root-cause-style failures with suggested files; `quality:documentation-map` keeps the documentation operating map, README document index, core source-of-truth rows, and cross-check commands from drifting; these gates run in the `ci:gate:runtime` or `ci:gate:static` lanes for PR feedback and in `ci:gate:release` for push/tags/dispatch evidence (`release.yml`, heavier perf smokes + uploaded artifacts).
- Local fault rehearsal: `pnpm fault:local` and `pnpm fault:local:stress` are explicit, non-CI operator drills that write `artifacts/operations/local_fault_lab.json`. The stress profile boots a Spark `local-cluster[2,1,512]`, kills a real executor JVM during a job, starts live Kafka plus PostgreSQL through Testcontainers, drives an 8-worker same-offset cursor-CAS storm, and restarts a bounded continuous archive worker over 80 broker events. The same evidence deliberately records two boundaries as `boundary_not_locally_proven`: managed Temporal multi-node failover and Kafka broker commit-unknown/rebalance callbacks still require infrastructure the current local worker architecture does not yet use.
- Object properties: SQLAlchemy `JSON` columns, not PostgreSQL `JSONB`.
- Commit-point risk tracking: [Commit-Point Risk Register](./commit-point-risk-register.md) now separates "feature works" from "the durable commit-point invariant is proven." Materialization watermarks have been hardened for the current MVP path: `action_log` pins `completed_at` plus `action_run_id`, and `object_snapshot` pins `active_index_version` plus tenant-scoped `object_change_sequence` while capturing output rows at run start. Object changes now append `object_record_versions`, so an old `object_snapshot` run can replay its stored watermark after later in-place object updates and still produce the original row hash/state. This prevents late-committed actions from being skipped, keeps failed action runs out of successful `ops.action_log` materialization rows, keeps same-cursor `action_log` reruns from duplicating rows inside the output, prevents a mid-run action from partly entering the same `ops.order_current` output, and makes old snapshot watermarks durable enough for replay evidence. `action_log` source reads now go through `MaterializationRepository.action_log_rows_at_watermark(...)`, so tenant/status/watermark filtering and object-edit patch joining happen at the repository query boundary instead of loading all action and edit rows into application memory first. Materialization metadata/outbox/lineage failure after storage promotion removes the promoted artifact, exposes no `materialization.completed` event for the failed run, and lets a same-cursor retry commit exactly one output version. Dataset/storage split-brain protection has also been hardened for the local MVP and MinIO/S3-compatible paths: storage promotion followed by DB metadata failure removes the promoted version artifact, FAILED sync runs keep `orphan_cleanup` evidence, committed versions with missing manifest/data files raise `committed_version_storage_missing`, local and S3 adapters verify manifest URI, byte size, and content hash after write, S3 additionally validates parquet footer readability plus manifest row count on commit/read, S3 partial multipart timeout cleanup prevents a partial object from becoming a committed version, same-version retry creates exactly one manifest/data pair, and S3 storage failures surface `adapterFailure` evidence in Operations. Dataset transaction finalization now rejects stale `SNAPSHOT` base versions before storage promotion and marks a transaction row committed only from `OPEN`, so a closed transaction cannot be re-committed as if it were still writable. Transform output/lineage atomicity now uses the dataset finalization boundary for post-commit metadata: if lineage insertion fails after output storage promotion, the promoted artifact is removed, no output version or lineage edge is served, and the transform run is marked `FAILED` with cleanup evidence. Compute-stage transform failure also deletes transaction staging artifacts, so a DuckDB OOM-like failure after writing a partial staged output leaves no committed output version and no partial staged file. Transform runs now store a `definition_snapshot` with the SQL template or Python source snapshot, input/output definition, checks, and source hash; failed-run retry replays that stored snapshot instead of reading the latest mutable transform definition. SQL transform execution rejects raw filesystem read functions such as DuckDB CSV path reads; transforms must use declared dataset inputs through the `{{ input('namespace.name') }}` template boundary. Python transforms now execute through `PythonTransformPlan` and `foundry_lite.transforms_sdk` handles (`Input.read_rows/read_pandas/read_polars`, `Output.write_rows/write_pandas/write_polars`), so user transform functions receive dataset handles rather than raw committed storage paths. Transform `mode="append"`/`"incremental"` now opens an APPEND dataset transaction for the output, while `mode="snapshot"` keeps the existing SNAPSHOT transaction. `foundry.transforms.run_graph(...)` provides a bounded downstream trigger entrypoint that runs transform definitions whose declared inputs consume the parent output dataset and records `transform.run.downstream_triggered` audit plus `triggered_downstream` run relation evidence. Transform scheduler preview/tick is also active for the bounded snapshot path: `foundry.transforms.preview_due(...)`, `foundry.transforms.run_due(...)`, `GET /api/transforms/scheduler/due`, `POST /api/transforms/scheduler/tick`, generated SDK `client.transforms.previewDue/tick(...)`, and `worker:transform-scheduler` compare latest input dataset versions against the latest successful run `input_versions`, skip active running transforms and missing input versions with `missingInputRefs`, rebuild due snapshot transforms, and record `transform.scheduler.triggered` audit plus `scheduled_rebuild_of` run relation evidence. The worker can run one tick or a configured bounded/continuous loop, stop on max ticks, empty ticks, or stop callback, and write JSON operator evidence. Append/incremental transform scheduler tick remains fail-closed until a duplicate-safe merge policy exists. This is not yet production lease/fencing/Kubernetes scheduler packaging, managed Temporal transform scheduling, or a full visual pipeline builder. Materialization execution now treats unknown `materialization_type` values as validation errors instead of falling through to the `object_snapshot` implementation. Stream/REST cursor commit-point proof now covers the local failure-injection path: if a stream batch or REST page is read but dataset writing fails, retry resumes from the last committed offset/cursor rather than the failed attempt's next cursor. REST page-number pagination is rejected as `non_replayable` instead of being treated like a cursor-safe source. Stream archive commit also rechecks the committed stream cursor after taking the dataset version-allocation lock, so parallel PostgreSQL-backed Kafka workers that read the same offset cannot both create committed dataset versions for that offset; the losing worker receives `ConflictDetected` and leaves one committed version. Action idempotency request-fingerprint proof now covers the current action path: same-key replay requires the same canonical request fingerprint, while same-key/different-body reuse returns `ConflictDetected` and leaves `action.run.idempotency_conflict` audit evidence. Action target invariants now reject requests whose object type differs from the action's declared target before idempotency-key reservation, reject corrupted target records whose internal object-type id differs before action-run insertion, and store the target API name from the action definition rather than the caller payload. Action commit atomicity proof now covers the current internal DB action path: failures at object mutation/edit/status/outbox/audit boundaries roll back together and no partial action evidence survives; the action idempotency winner insert now uses conflict-ignore semantics instead of a savepoint that could escape outer rollback on SQLite. Real S3/MinIO external writeback proof now covers outcome-unknown timeouts, landed-write/local-failure compensation, and real `remote_lookup` reconciliation through `ExternalWritebackAdapter` and `S3ExternalWritebackAdapter`; bounded `worker:writeback-reconciliation` recovery now drains unresolved rows that carry stored `externalWritebackUri` evidence and records `action.writeback.recovery_tick` audit evidence, while standing review queues, always-on managed compensation daemons, ERP-specific reverse/compensation execution, and ERP-specific connector packaging remain future. Runtime outbox inserts now convert only the expected tenant/event/idempotency duplicate into idempotent replay; unrelated DB integrity errors are re-raised. Remaining gaps: full Kafka group rebalance revoke fencing and broker commit-unknown reconciliation still need failure injection, and external-writeback compensation still needs a managed review/approval queue, always-on daemon packaging, and ERP-specific reverse/compensation executor beyond the current operator/bounded-worker reconciliation entrypoints.

- Object index reindexing: `ObjectStore.shadow_reindex` can build a shadow object index namespace, validate count/hash against the active baseline, replay action edit properties into the shadow rows, switch the active serving pointer through the object-type-level `object_index_versions.active_index_version` registry, and keep failed validation from replacing the previous active index. Row-level `index_version`/`is_active` flags still mark which object/link rows are served, but the active version is no longer inferred only from rows, so an object type with `0` rows can still preserve `index_run_*` as the version CDC/search workers should target. Shadow promotion uses a compare-and-swap check against the previously validated active version: if another switch wins first, the later switch fails instead of silently overwriting the pointer. Object Query cursor tokens now include the serving `active_index_version`; if a user fetches page 1 before shadow promotion and asks for page 2 after promotion, the cursor is rejected instead of mixing old/new index pages into duplicate or missing rows. The pointer row id is unique per insert attempt, while the conflict target remains the natural pointer key `tenant_id` plus `object_type_id`; this prevents concurrent first pointer creation from escaping the upsert path through a primary-key-only collision. A full reindex over the active index version is now idempotent: when the source dataset version, base patch, and merged properties are unchanged, the reindex skips the per-object update so it does not bump `object_version` or emit a spurious `object.changed` event, which keeps a held `expectedObjectVersion` valid after a replay. Object read, link read, object set membership, and materialization reads filter to active rows. `quality:shadow-reindex` plus `tests/integration/test_cdc_object_indexing.py` prove the local/fake, SQLite, and Postgres repository contracts, success/failure integration flows, the zero-row CDC follow-up case through `test_empty_shadow_reindex_persists_active_pointer_for_next_cdc_insert`, stale pointer rejection through `test_object_index_repository_contract_rejects_stale_shadow_pointer_switch`, active-index cursor rejection through `test_shadow_reindex_alias_switch_cursor_version_safe`, and a real PostgreSQL concurrent first-pointer race through `test_object_index_repository_contract_concurrent_first_pointer_switch_has_one_winner`. `VERIFY-ACTIVE-INDEX-POINTER-FLAKE` repeats that race `10` times against PostgreSQL to prove the old primary-key-vs-natural-key race is stable. API/CLI/Web operator controls for starting this shadow path are not yet exposed beyond the core facade.
- Search projection: `SearchIndexAdapter` now includes ontology-derived `SearchIndexMapping`, full-text `SearchQuery`, document id listing for drift checks, and local/fake/Elasticsearch-compatible adapter contracts. `ElasticsearchAdapter` is optional behind `foundry-lite[elasticsearch]` and the `FOUNDRY_LITE_SEARCH_PROFILE=elasticsearch` composition-root switch, while object store remains the source of truth. The API object query payload `search` field and `ObjectStore.query(..., search_text=...)` route searchable property full-text requests through the search adapter, then re-read active object records for masking and stale/orphan protection. Search hits expose the search projection version separately from the current object version, so a stale hit can be shown as stale while action entry still uses the fresh object-store state. ## Refactor Pointers

These are known design debts that are currently gated (so they cannot regress) but
should be paid down on a planned timeline. They are not bugs; they are deliberate
intermediate states.

- **Application Service canonicalization.**
  `FoundryLite` no longer composes service capabilities through Python
  multiple inheritance. It is a platform root that exposes one thin facade per
  bounded context (`DatasetWorkspace`, `TransformPipeline`, `OntologyRegistry`,
  `ObjectStore`, `ActionGateway`, `MaterializationRunner`, `OperationsConsole`,
  `SupplyChainDemo`), each holding explicit public forwarders,
  while `CoreServices` constructs Action, Dataset, Object, Transform, Ontology,
  Materialization, Runtime, and Demo service groups or focused services
  services with service-specific dependency injection. A service receives only
  the `CoreDependencies` fields listed in its `required_dependencies`; for
  example, `ActionApplyService` receives `engine`, `policy`, and
  `action_repository`, not storage or transform adapters. A service also
  receives only the collaborator services listed in its `required_collaborators`;
  for example, `ActionApplyService` receives writeback, runtime, ontology,
  object-record, object-indexing, and OSDK-scope collaborators, not all
  services. Cross-service helper access now uses
  explicit collaborator attributes such as `runtime_service._audit(...)` rather
  than `__getattr__` method lookup. These rules are held in check by static gates:
  `check_service_dependencies.py`, `check_service_call_graph.py`, Tach, AST-grep,
  and the application-size cap. This keeps the
  public API stable while removing facade-level MRO risk before Workflow /
  Stream / Search / Connector / Auth boundaries are extracted.
- **Remaining Facade compatibility debt.**
  The flat service method registry and `FoundryLite.__getattr__` /
  `FoundryLite.__setattr__` monkeypatch bridge have been removed. The
  remaining compatibility cost is the explicit public forwarder list spread
  across the bounded-context sub-facades, which keeps API/CLI/test entrypoints
  stable while services continue to evolve independently.

- Transform bounded-context split: Transform is now split into pure domain rules plus explicit application use-case services for definition, run, scheduler, graph, and the current partial transform row-DLQ replay path. `TransformService` remains as the compatibility entrypoint for `foundry.transforms.*`, API callers, and SDK-facing contracts, while `TransformServices` registers the subservices in the dependency/collaborator graph so quality gates can inspect each responsibility separately. Action bounded-context split is also current: `ActionService` remains the compatibility entrypoint for `foundry.actions.*`, API callers, Operations writeback controls, and SDK-facing contracts, while `ActionServices` registers apply, validation, and writeback use-case services separately.
- Domain Rule Kernel split: common platform rules for idempotency replay/conflict, terminal state transitions, write-traffic blocking, evidence redaction, and OSDK resource-scope vocabulary are now in `libs/foundry_lite/domain/platform`. Object CDC ordering/stale-event/tombstone rules, object indexing duplicate-source/shadow-validation/source-missing/conflict decisions, backup/restore resume approval plus artifact restore eligibility rules, dataset quality policy/default-primary-key rules, and Ontology migration compatibility/reindex-contract rules now have focused domain modules as well. Services still own transactions, repositories, audit, outbox, and external adapters; they call domain rules instead of re-encoding those decisions inline.
- Runtime evidence boundary: `RuntimeEvidenceService` now owns the shared audit/outbox/lineage/run-relation/error-payload/write-traffic helper boundary. `RuntimeService` remains the Operations read/retry compatibility entrypoint and delegates evidence writes to that internal boundary without adding a new public service-call graph level.
- ObjectIndexing bounded-context split: object indexing is now split into a stable compatibility entrypoint plus explicit CDC, rebuild, source-link, shadow promotion, record-mutation/evidence, and ontology-reindex use-case services. Other application services no longer depend on the compatibility entrypoint for merge/rebuild work; they call the focused collaborator they actually need. Object indexing mixins have been removed from the `quality:no-service-mixin-growth` allowlist.
- BackupRestore bounded-context split: backup/restore is now split into a stable compatibility entrypoint plus explicit preflight, restore-mode, artifact creation, artifact verification, historical artifact execution, and validation use-case services. Backup/restore application mixins have been removed from the `quality:no-service-mixin-growth` allowlist, while restore resume and artifact eligibility decisions live in `domain/backup_restore` with direct tests.
- DatasetQuality bounded-context split: dataset quality is now split into a stable compatibility entrypoint plus explicit API, contract-definition, and commit-time runtime services. Data-quality warning/blocking/default-check decisions live in `domain/dataset/quality`, while transaction, repository, audit, and Operations evidence remain in application services. Dataset quality API/contracts mixins have been removed from the `quality:no-service-mixin-growth` allowlist.
- Ontology bounded-context split: ontology is now split into a stable compatibility entrypoint plus explicit activation/import, active-catalog, lookup, and object-reindex-contract services. Ontology migration compatibility, SDK-breaking classification, deterministic object reindex operation keys, and reindex contract completion payload rules live in `domain/ontology`, while activation transactions, repository reads/writes, audit, and outbox remain in application services. Ontology reindex contract mixin debt has been removed from the `quality:no-service-mixin-growth` allowlist.
- Mixin debt boundary: `OsdkApplicationService` is now a thin entrypoint over explicit client, scope, SDK, and idempotency use-case services. New service/facade `*Mixin` growth is blocked by `quality:no-service-mixin-growth`, and new domain rule/specification files require direct tests through `quality:domain-rule-tests`. Remaining allowlisted mixin debt is runtime observability and Operations Console backup compatibility; those are follow-up refactor targets, not current feature gaps.

## Quality Signal Boundaries

- Branch coverage is the main behavior gate.
- Public callable coverage means "a public callable was executed at least once"; it is not a substitute for branch/path coverage.
- CI enforces `0` `core._...` private facade references in tests. Some lower-level tests still target service/helper modules directly to pin failure edges, but the public facade no longer exposes or forwards private helper methods.
